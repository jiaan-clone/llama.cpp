# week2 day3

## 习题1
闭卷写出 Day 2 的 Q/K/V shape 和 cache 估算公式。

答：

沿用 Day 2 使用的 `deepseek-r1-1.5b-f16.gguf`（Qwen2 架构）参数：

```text
D   = 1536       hidden/embedding size
H   = 12         Query head 数
KvH = 2          Key/Value head 数
Dh  = D / H = 128
L   = 28         Transformer block 数
```

对于本次输入的 `N` 个 token，Q/K/V 的逻辑 shape 为：

```text
hidden [N, 1536]
  -> Q [N, 12, 128]
  -> K [N,  2, 128]
  -> V [N,  2, 128]
```

Q 的总维度为 `H * Dh = 1536`；K 和 V 各自的总维度为
`KvH * Dh = 256`。这是 GQA：每 `H / KvH = 6` 个 Query head
共享一个 K head 和一个 V head。若继续计算 attention，score 的逻辑
shape 为 `[H, N, S] = [12, N, S]`，其中 `S` 是当前 Query 可见的
历史和当前 KV 位置数。

KV cache 只保存 K 和 V，因此单层、单 sequence 的最小元素数为：

```text
elements per layer = 2 * S * KvH * Dh
```

其中第一个 `2` 表示 K、V 两份。所有 `L` 层的元素数和字节数分别为：

```text
elements for all layers = 2 * S * KvH * Dh * L
bytes for all layers    = 2 * S * KvH * Dh * L * bytes_per_element
```

假设 K/V cache 使用 F16（`bytes_per_element = 2`），并取 `L=28`：

| 可见长度 `S` | 单层 K+V 元素数 | 全 28 层元素数 | 全 28 层 F16 字节数 |
| ---: | ---: | ---: | ---: |
| `128` | `65,536` | `1,835,008` | `3,670,016` bytes = `3.5 MiB` |
| `4096` | `2,097,152` | `58,720,256` | `117,440,512` bytes = `112 MiB` |

这里的 `N` 是本次 decode 输入 token 数，`S` 是可见的历史长度；二者都
不是训练 context length `n_ctx_train` 或运行时配置的 `n_ctx`。上述数值是
只计 K/V 有效元素的理论最小估算，不等同于实际 `llama_memory_i` 的分配量。

## 习题2
找公共入口**：阅读 [`src/llama.cpp`](../../../../src/llama.cpp) 的 `llama_model_load_from_file_impl()`、`llama_model_load()` 和 `llama_model_load_from_file()`。画出公共 API 至 `llama_model_load()` 的调用图，标出 `llama_model_params` 在哪里传入。

答：

以最常用的按路径加载入口为主，调用图如下（源码行号以当前版本为准）：

```text
调用方
  |
  | path_model, params
  v
llama_model_load_from_file(path_model, params)       [src/llama.cpp:451-456]
  |  public API；params 按值传入
  |  splits = {}
  v
llama_model_load_from_file_impl(
    metadata=nullptr, set_tensor_data=nullptr,
    path_model, splits, file=nullptr, params)        [src/llama.cpp:366-429]
  |  params 按值传入；检查唯一输入源、backend，补默认 progress_callback
  v
llama_model_load(..., params)                        [src/llama.cpp:304-364]
  |  params 以 llama_model_params & 引用传入
  +--> llama_model_loader ml(... params.load_mode, params.check_tensors,
  |        params.no_alloc, params.load_mtp, params.kv_overrides,
  |        params.tensor_buft_overrides)
  +--> llama_model_create(ml, params)
  +--> llama_prepare_model_devices(params, model)
  +--> model->load_hparams(ml) / load_vocab(ml)
  +--> vocab_only 时返回；否则 model->load_tensors(ml)
```

因此，公共 API 到核心加载函数的最短路径是：

```text
llama_model_load_from_file(path, params)
  -> llama_model_load_from_file_impl(..., params)
  -> llama_model_load(..., params)
```

`llama_model_load_from_file_impl()` 先确认 `metadata`、`path_model`、`file`
三种输入源中恰好有一种，再初始化 GGML 时间、检查 backend，并在调用方没有
提供 `progress_callback` 时写入一个默认的进度回调。之后它检查
`llama_model_load()` 返回的状态：`-1` 表示加载错误，`-2` 表示被回调取消，成功
时返回模型指针。

参数传递有一个容易忽略的细节：`llama_model_load_from_file()` 和
`llama_model_load_from_file_impl()` 的 `params` 都是**按值**接收；只有
`llama_model_load()` 的形参是 `llama_model_params &`。所以最后的引用指向的是
`impl` 内部的参数副本，不会把 `impl` 对默认进度回调等字段的修改写回最初的
调用方对象。`llama_model_load()` 内部则复用该副本，把相关字段分发给
loader、模型构造、设备准备和 tensor 加载阶段。

另外，旧的 `llama_load_model_from_file(path, params)` 只是弃用兼容包装，先转调
`llama_model_load_from_file()`，不会形成另一条独立的加载路径。

## 习题3
读 loader 构造：阅读 [`src/llama-model-loader.cpp`](../../../../src/llama-model-loader.cpp) 的 `llama_model_loader::llama_model_loader()`。为下面每步补一行“输入、结果、尚未读取的内容”：

   ```text
   path_model
     -> gguf_init_from_file(... no_alloc = true)
     -> general.architecture -> llm_arch
     -> llama_file + GGML metadata context
     -> tensor metadata -> weights_map
     -> split.count / split.no validation -> extra files and contexts
   ```

   特别写明 `no_alloc = true` 在这里避免的是为 tensor data 分配/读取，不是让 metadata 消失。

答：

以下按 `fname = path_model` 的主文件加载分支说明（构造函数还支持外部
`metadata` 和 `FILE *` 两种输入）：

| 步骤 | 输入 | 结果 | 此时尚未读取/完成的内容 |
| --- | --- | --- | --- |
| `path_model` | `fname`、可选的 `splits` 列表，以及 loader 的 `load_mode` 等参数 | 因为 `fname` 非空，选择“从主 GGUF 路径加载”的分支；尚未打开主文件 | tensor data、架构专用 hparams、模型对象和 tensor placement 都还没有处理 |
| `gguf_init_from_file(... no_alloc = true)` | `fname`；`gguf_init_params{ no_alloc=true, ctx=&ctx }` | `metadata_ptr` 得到 GGUF metadata context，`ctx` 得到只含 tensor 描述的 GGML context；GGUF 的 KV、tensor name/type/shape/offset 和 data section 信息已可查询 | 不为 tensor binary blob 分配内存，也不把 tensor data 读入 `ctx` |
| `general.architecture -> llm_arch` | 上一步的 `metadata`，读取 `general.architecture` | `arch_name` 保存架构字符串；`llm_arch_from_string(arch_name)` 的结果用于初始化 `llm_kv`，后续 `get_key(LLM_KV_...)` 才能按该架构生成 metadata key | 还没有调用 `model->load_hparams()`，所以 embedding、head、layer 等模型 hparams 尚未装入 `llama_model` |
| `llama_file + GGML metadata context` | `fname`、`ctx`、`metadata`、`use_direct_io` | 创建并保存 `llama_file` 到 `files`；把 `ctx` 保存到 `contexts`；后续每个 tensor weight 可以用文件句柄和 GGUF offset 定位 | 文件句柄已建立，但 tensor bytes 仍未读取；也没有 mmap、后端 buffer 或设备放置 |
| `tensor metadata -> weights_map` | `ctx` 中的每个 metadata-only `ggml_tensor`，以及主文件的 `metadata` | 遍历 tensor descriptors，拒绝重复 name；累计 `n_elements`/`n_bytes`；以 tensor name 建立 `weights_map`，每项保存源文件索引、数据 offset 和 descriptor | `weights_map` 只是索引和描述，不是权重数据本身；额外 split 的 tensor 尚未加入 |
| `split.count / split.no validation -> extra files and contexts` | 主文件 metadata 中的 `split.count`，多 split 时的 `split.no`，以及可选 `splits` | `split.count > 1` 时要求主文件 `split.no == 0`；若未提供列表则用 `llama_get_list_splits()` 生成并检查数量；逐个以 `no_alloc=true` 打开其余 GGUF，校验每个 `split.no`，保存 `llama_file`/GGML context，并把其 tensor descriptors 合并进 `weights_map`；最后核对 `split.tensors.count` 与 map 大小 | 仍只完成 metadata/index 合并，未加载任何 split 的 tensor binary data，也未进行模型 tensor 创建、buffer 分配或 placement |

这里的 `no_alloc = true` 是传给 `gguf_init_params` 的开关。GGUF loader 仍然会
读取并保存 metadata 和 tensor info；它只是让为 tensor data 准备的 GGML context
不分配 binary blob，也不读取那段权重字节。后续 `llama_model_load()` 继续到
`model->load_tensors(ml)` 时，才会根据 `weights_map` 的 offset 通过 mmap 或普通
文件读取取得实际 tensor data。因此，“no alloc”不等于“没有 metadata”。构造函数
形参中的 `no_alloc` 还会在末尾保存到 `this->no_alloc`，这是后续模型加载阶段的
另一个状态，不能与 GGUF 初始化参数混为一谈。

## 习题4
处理 split 分支：对照 `llama_get_list_splits()` 与构造函数的 `n_split > 1` 分支，画出单文件与多 split 的差异。手写一个假想文件名 `model-00001-of-00004.gguf`，说明为什么加载必须从第一个 split 开始，以及 `weights_map` 为什么不允许重复 tensor name。

答：

### 单文件与多 split

```text
单文件（没有 split.count，或 split.count <= 1）

fname
  -> gguf_init_from_file(fname, no_alloc=true)
  -> files[0] + contexts[0]
  -> 扫描主文件 tensor metadata
  -> weights_map[name] = { file_idx=0, offset, descriptor }
  -> 完成 loader metadata/index 初始化
```

单文件只建立一个 `llama_file`、一个 GGML metadata context，并把主文件的
tensor descriptor 放入 `weights_map`；不会调用 `llama_get_list_splits()`，也
不会进入 `for (idx = 1; idx < n_split; idx++)` 的额外文件循环。

```text
多 split（split.count = n_split > 1）

第一个 split（必须是 split.no = 0）
  -> gguf_init_from_file(..., no_alloc=true)
  -> 校验主文件 split.no == 0
  -> llama_get_list_splits() 或使用调用方提供的 splits
  -> 检查 splits.size() == split.count
  -> idx = 1 .. n_split-1:
       打开 split[idx]，以 no_alloc=true 读取 metadata
       校验该文件的 split.no == idx
       保存 file/context，并把 tensor descriptor 合并到 weights_map
  -> 校验 split.tensors.count == weights_map.size()
```

因此，多 split 的加载仍然先处理第一个 shard，然后把其余 shard 的 metadata
和权重定位信息合并成一个统一索引；此阶段仍不读取 tensor binary data。

### `model-00001-of-00004.gguf` 示例

假设传入：

```text
model-00001-of-00004.gguf
```

GGUF 文件名是人类可读的 1-based 编号，但 metadata 中的 `split.no` 使用
0-based 编号：`00001` 对应 `split.no = 0`，`split.count = 4`。因此构造函数
接受该文件作为主文件后，若 `splits` 为空，会调用：

```text
llama_get_list_splits("model-00001-of-00004.gguf", idx=0, n_split=4)
```

`llama_split_prefix()` 提取前缀 `model`，再由 `llama_split_path()` 生成有序列表：

```text
[
  "model-00001-of-00004.gguf",  // split.no = 0，主文件
  "model-00002-of-00004.gguf",  // split.no = 1
  "model-00003-of-00004.gguf",  // split.no = 2
  "model-00004-of-00004.gguf"   // split.no = 3
]
```

如果调用方直接把 `model-00002-of-00004.gguf` 作为 `fname`，该文件的
`split.no` 应为 `1`；构造函数在 `n_split > 1` 分支要求主文件 `idx == 0`，
因此会报错 `model must be loaded with the first split`，不会从中间 shard
开始拼接。必须从第一个 split 开始，才能建立完整且有序的 shard 列表，先纳入
第一个 shard 的 tensor metadata，再验证并追加后续 shard。

### 为什么 `weights_map` 不允许重复 tensor name

`weights_map` 以 tensor name 为 key，每个 value 保存该 tensor 唯一的源文件索引
`idx`、文件内 offset 和 GGML descriptor。主文件和每个额外 split 扫描 tensor
时都会先执行 `weights_map.find(tensor_name)`；已存在就抛出
`invalid model: tensor '...' is duplicated`，而不是覆盖旧项。

分片模型应当把不同 tensor 分布到不同文件，同一个 name 只能对应一个实际权重。
如果允许重复，后加入的 shard 可能覆盖先加入的 `idx/offset`，loader 就无法
确定应从哪个文件读取该 tensor，可能导致权重丢失或错误加载。最后对
`split.tensors.count` 与 `weights_map.size()` 的检查，也依赖这个“一名一项”的
不变量来发现缺失、重复或损坏的 shard。

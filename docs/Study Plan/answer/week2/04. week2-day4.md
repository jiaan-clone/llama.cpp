# week2 day4

## 习题1
闭卷画出 Day 3 的 `path_model -> loader -> arch` 链路。

答：

以当前使用的 `deepseek-r1-1.5b-f16.gguf` 为例，主路径如下：

```text
调用方
  | path_model, llama_model_params
  v
llama_model_load_from_file(path_model, params)             [公共 API]
  | params 按值传入；初始化 splits = {}
  v
llama_model_load_from_file_impl(
    metadata=nullptr, set_tensor_data=nullptr,
    path_model, splits, file=nullptr, params)
  | 校验唯一输入源、初始化时间/backend、补默认 progress_callback
  v
llama_model_load(..., params)                              [params &]
  | 将 fname=path_model 和 loader 参数传入
  v
llama_model_loader ml(..., fname, splits, ...)
  |
  | fname 非空时：
  |   gguf_init_from_file(fname, { no_alloc=true, ctx=&ctx })
  |     -> metadata_ptr / metadata：GGUF KV 与 tensor info
  |     -> ctx：metadata-only 的 GGML tensor descriptors
  |   -> 读取 general.architecture 到 arch_name
  |   -> llm_arch_from_string(arch_name)
  |   -> llm_kv = LLM_KV(得到的 enum)
  |   -> files、contexts、weights_map，以及必要的 split metadata/index
  v
llama_model_create(ml, params)
  -> ml.get_arch() 返回 llm_kv.arch
  -> 未知架构则报错；已知架构进入对应模型工厂分支
```

这条链路中各对象的职责是：

| 阶段 | 输入 | 结果 | 尚未完成的内容 |
| --- | --- | --- | --- |
| 公共 API | `path_model`、`params` | 将路径包装成内部 loader 调用；`metadata`/`FILE *` 为空 | 尚未解析 GGUF |
| `llama_model_loader` 构造 | `fname`、split 列表、load mode 等 | 读取 GGUF metadata 和 tensor descriptors，建立文件/context 及权重索引 | tensor binary data 尚未通过 mmap/普通读取加载 |
| architecture 解析 | `metadata[general.architecture]` | `arch_name` 字符串经 `llm_arch_from_string()` 变为 `LLM_ARCH_*`，保存在 `llm_kv.arch` | 尚未读取通用/架构专用 hparams，尚未创建具体模型对象 |
| `llama_model_create(ml, params)` | `ml.get_arch()` 与模型参数 | 根据 arch 选择具体 C++ 模型类；未知 arch 直接失败 | 后续才进入设备准备、`load_hparams()`、词表和 tensor 加载 |

对本题模型，metadata 中的：

```text
general.architecture = "qwen2"
  -> llm_arch_from_string("qwen2")
  -> LLM_ARCH_QWEN2
  -> llama_model_create(ml, params)
  -> llama_model_qwen2(params)
```

需要区分两个时刻：`llama_model_loader` 构造阶段的
`gguf_init_from_file(... no_alloc = true)` 已经读入 metadata 和 tensor
描述，但没有读入权重字节；真正的 tensor buffer、hparams、vocab 和权重数据在
`llama_model_load()` 后续的固定顺序中才会继续处理。因此 `arch` 先于
`load_hparams()` 得到，模型工厂可以先根据它创建正确的模型子类。

## 习题2
读模型工厂：阅读 [`src/llama-model.cpp`](../../../../src/llama-model.cpp) 中的 `llama_model_create(llama_model_loader &, ...)`、`llama_model_create(llm_arch, ...)` 和 `llama_model_mapping()`。只跟踪当前模型对应的 `LLM_ARCH_*` 分支；不要逐个阅读其他模型类。

答：

本题只跟踪当前 `deepseek-r1-1.5b-f16.gguf` 的 Qwen2 分支。三个函数的
关系是：

```text
llama_model_create(llama_model_loader & ml, params)
  |
  | arch = ml.get_arch()
  |   -> 返回 ml.llm_kv.arch
  |   -> arch == LLM_ARCH_UNKNOWN 时抛出
  v
llama_model_create(llm_arch arch, params)
  |
  | model = llama_model_mapping(arch, params)
  v
llama_model_mapping(LLM_ARCH_QWEN2, params)
  |
  +--> new llama_model_qwen2(params)
  v
设置 model->arch = LLM_ARCH_QWEN2
  |
  +--> 若 split_mode == LLAMA_SPLIT_MODE_TENSOR，检查 Qwen2 是否支持
  v
返回 llama_model *
```

### 三个工厂函数的职责

| 函数 | 输入 | 当前模型上的行为 | 失败含义 |
| --- | --- | --- | --- |
| `llama_model_create(llama_model_loader &, params)` | loader 中已解析的 `llm_kv.arch`、`params` | 调用 `ml.get_arch()`，将 loader 的架构结果转交给 arch 重载 | `LLM_ARCH_UNKNOWN` 表示 metadata 中架构缺失或无法识别，直接抛出 `unknown model architecture` |
| `llama_model_create(llm_arch, params)` | `LLM_ARCH_QWEN2`、`params` | 调用 `llama_model_mapping()` 得到对象；设置 `model->arch`；检查 tensor split 模式支持 | 不支持的 `LLAMA_SPLIT_MODE_TENSOR` 配置抛出错误；mapping 的 default 分支表示架构没有实现 |
| `llama_model_mapping(arch, params)` | 枚举 `arch`、`params` | switch 命中 `case LLM_ARCH_QWEN2`，执行 `new llama_model_qwen2(params)` | 未命中任何 case 时抛出 `unsupported model architecture` |

`llama_model_qwen2` 的构造函数只把参数传给基类：

```cpp
llama_model_qwen2(const llama_model_params & params)
    : llama_model_base(params) {}
```

它在这里的意义是创建具有 Qwen2 虚函数实现的具体 C++ 对象；此时还没有
调用 `load_arch_hparams()` 或 `load_arch_tensors()`。回到
`llama_model_load()` 后，固定顺序才会继续执行 `llama_prepare_model_devices`、
`model->load_hparams(ml)`、`model->load_vocab(ml)`、`model->load_stats(ml)` 和
`model->load_tensors(ml)`。因此模型工厂只解决“应该实例化哪个模型类”，不负责
读取 hparams、词表或权重数据。

对本模型可以把工厂结论压缩为：

```text
GGUF general.architecture = "qwen2"
  -> llm_arch = LLM_ARCH_QWEN2
  -> llama_model_mapping(...)
  -> llama_model_qwen2(params)
  -> model->arch = LLM_ARCH_QWEN2
```

## 习题3
读固定加载顺序**：回到 `llama_model_load()`，为下面步骤写明依赖关系与失败时的含义：

   ```text
   llama_model_loader
     -> llama_model_create
     -> llama_prepare_model_devices
     -> load_hparams
     -> load_vocab
     -> load_stats
     -> load_tensors
   ```

   解释为什么架构、hparams 和 vocab 必须在 `load_tensors()` 前可用；说明 `vocab_only` 会停止在哪一步，以及它不等于 tokenizer 不需要 metadata。

答：

`llama_model_load()` 的主流程是严格的前后顺序；前一步成功建立的对象和状态
才会交给后一步：

```text
llama_model_loader ml
  |  GGUF metadata、架构、tensor descriptor/weights_map 已可用
  v
llama_model_create(ml, params)
  |  根据 ml.get_arch() 创建具体模型对象
  v
llama_prepare_model_devices(params, model)
  |  给模型准备 CPU/GPU/meta device 列表
  v
model->load_hparams(ml)
  |  通用 hparams + Qwen2 的架构专用 hparams
  v
model->load_vocab(ml)
  |  根据 arch 从 metadata 建立 tokenizer/vocab
  v
model->load_stats(ml)
  |  复制 loader 的 n_elements/n_bytes
  v
params.vocab_only ? 返回 model : model->load_tensors(ml)
```

| 步骤 | 依赖与完成内容 | 失败时的含义/状态 |
| --- | --- | --- |
| `llama_model_loader` | 依赖输入路径或 metadata；构造 GGUF metadata、架构枚举、文件/context 和 `weights_map`。它只建立描述和偏移索引，不负责模型对象或后端 buffer | 构造函数的 GGUF 解析、split 校验、重复 tensor name 等异常会被最外层 `catch` 捕获，最终返回 `-1` |
| `llama_model_create` | 依赖 loader 已解析的 `llm_arch`；当前模型命中 `LLM_ARCH_QWEN2`，创建 `llama_model_qwen2` | unknown/unsupported architecture，或不支持的 tensor split 配置，抛异常并以 `-1` 结束；后续步骤不会执行 |
| `llama_prepare_model_devices` | 依赖已创建的 model 和 `llama_model_params`；建立设备列表、tensor-parallel meta device，并检查 `main_gpu` 等参数 | 返回 `false` 表示没有可用设备、tensor split 没有设备或 GPU 选择无效，`llama_model_load()` 立即返回 `-1` |
| `load_hparams` | 依赖 `ml.metadata` 与已确定的 `arch`；读取通用 context/embedding/layer/head/RoPE 等字段，再调用 `load_arch_hparams(ml)` | 缺 key、类型错误、数值不合法或架构专用 hparams 失败，会包装为 `error loading model hyperparameters`，最终 `-1` |
| `load_vocab` | 依赖 `arch` 以构造 `LLM_KV(arch)`，并依赖 metadata 中 tokenizer model、tokens、scores/merges、special-token IDs 等数组/字段 | tokenizer metadata 缺失或格式错误会包装为 `error loading model vocabulary`，最终 `-1` |
| `load_stats` | 依赖 loader 已累计的 `n_elements`/`n_bytes`；把统计值写入 model impl | 当前函数本身无返回值和独立失败分支；如果 loader 状态无效，问题应已在前面的 loader 阶段暴露 |
| `load_tensors` | 依赖 arch、hparams、vocab、devices 和 `weights_map`；按架构创建 tensor descriptors，按 hparams/vocab 决定 shape，分配/建立 buffer，最后 mmap 或普通读取 tensor data | 返回 `false` 时表示进度回调取消，`llama_model_load()` 返回 `-2`；后端、shape、必需 tensor 或 buffer 异常则由外层捕获并返回 `-1` |

### 为什么架构、hparams 和 vocab 必须在 `load_tensors()` 前完成

- **架构必须先确定。** `load_tensors()` 通过多态调用
  `load_arch_tensors(ml)`，并用 `LLM_TN(arch)` 生成 tensor 名称；没有
  `LLM_ARCH_QWEN2` 就无法选择正确的 tensor 声明和模型类。
- **hparams 必须先加载。** `n_layer_all` 决定要创建多少层，`n_embd`、`n_ff`、
  head 数等决定各权重的 shape；设备分配和 `n_gpu_layers` 也需要这些值，buffer
  大小必须在读取权重前确定。
- **vocab 必须先加载。** `load_tensors()` 的 `LLAMA_LOAD_LOCALS` 使用
  `vocab.n_tokens()` 作为 `n_vocab`，以创建 token embedding、output 等 tensor；
  vocab 还决定 tokenizer 和 special-token 相关的模型状态。

### `vocab_only` 的停止点

`params.vocab_only` 在进入 `llama_model_load()` 时先写入
`model->hparams.vocab_only`。因此：

1. `load_hparams()` 仍会复制非数组 metadata、读取 `general.name`，但在
   `hparams.vocab_only` 为 true 时跳过后续通用/架构 hparams 的读取。
2. 仍然执行 `load_vocab()`，因为词表本身就是 vocab-only 模式的目标。
3. 仍然执行 `load_stats()`。
4. 在 `load_tensors()` 之前命中 `if (params.vocab_only)`，记录
   `vocab only - skipping tensors` 并返回成功的 model；因此不会创建/加载权重
   tensor buffer。

这说明 `vocab_only` 只是“不加载模型权重 tensor”，不是“不需要 metadata”。架构
选择依赖 `general.architecture`，`load_hparams()`/`load_vocab()` 依赖 GGUF 的
tokenizer metadata（如 `tokenizer.ggml.model`、tokens、scores/merges 和 special
token IDs）；没有这些 metadata，就无法得到正确的 tokenizer/vocab，即使完全不
进入 `load_tensors()` 也一样。

## 习题4
定位多态边界：阅读 [`src/llama-model.h`](../../src/llama-model.h) 中 `llama_model` 和 `llama_model_base` 的虚函数声明。画出一张小表，列出 `load_hparams()` 的通用部分、`load_arch_hparams()` 的架构变化点、`load_vocab()`、`load_arch_tensors()` 与 `build_arch_graph()` 的职责。最后一项只标边界，不读实现。

答：

`llama_model`（`src/llama-model.h:689-697`）定义加载和图构建的虚接口，
`llama_model_base`（`src/llama-model.h:741-749`）实现通用流程，同时把
架构差异保留为三个纯虚函数。当前 Qwen2 对象由工厂创建后，下面这些调用会
通过虚函数分派到基类或 `llama_model_qwen2`：

| 方法 | 所在层 | 主要职责 | 当前 Qwen2 的变化点/边界 |
| --- | --- | --- | --- |
| `load_hparams(ml)` | `llama_model_base` 的通用实现 | 从 GGUF metadata 复制可查询的 scalar KV，读取 `general.name`；读取 context length、embedding length、block count、expert、attention head/KV head、FFN、RoPE 等通用 hparams；设置派生的 head/rotary/rope 状态；最后调用 `load_arch_hparams(ml)` | 通用字段和校验由基类负责；`vocab_only` 或 CLIP 会在架构 hparams 之前提前结束，因此不会完成完整推理 hparams |
| `load_arch_hparams(ml)` | 具体模型类的纯虚接口 | 读取只有该架构知道的 metadata，并补充/推导架构专用状态 | `llama_model_qwen2` 读取 RMSNorm epsilon，并根据 layer/embedding/head 等值推导模型 `type`；它由基类 `load_hparams()` 在通用部分末尾调用 |
| `load_vocab(ml)` | `llama_model_base` 的通用实现 | 用当前 `arch` 构造 `LLM_KV(arch)`，调用 `vocab.load(ml, kv)` 解析 tokenizer model、tokens、scores/merges 和 special-token metadata | 词表解析是共享流程，但 key namespace 由 `arch` 决定；不负责读取模型权重 |
| `load_arch_tensors(ml)` | 具体模型类的纯虚接口 | 声明该架构的权重 tensor 名称、shape 和可选/重复等 flags；由通用 `load_tensors()` 在设备和 buffer 规划后调用 | Qwen2 分支声明 embedding、output、attention Q/K/V、FFN 和各层 norm 等 tensor；实际 buffer 分配、mmap/读取由基类 `load_tensors()` 负责 |
| `build_arch_graph(params)` | 具体模型类的纯虚接口 | 在模型已加载后，为该架构提供计算图构建入口 | 这里只标出多态边界：通用 graph 包装层把请求转交给架构类；本题不展开其 graph op 实现 |

可以把职责边界压缩为：

```text
通用基类 llama_model_base
  load_hparams(common metadata)
    -> load_arch_hparams(architecture-specific metadata)
  load_vocab(shared tokenizer loader)
  load_tensors(common device/buffer/data path)
    -> load_arch_tensors(architecture-specific tensor declarations)

具体架构类
  build_arch_graph(architecture-specific graph boundary)
```

因此，“通用”不表示完全不依赖架构：`load_hparams()` 负责公共字段和调用时机，
`load_vocab()` 使用 `arch` 选择 metadata key，`load_tensors()` 使用 `arch` 和
hparams 建立通用加载环境；真正需要模型知识的字段、权重命名/shape 和计算图，
才越过虚函数边界交给 Qwen2 实现。

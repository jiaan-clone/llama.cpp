## 习题1
不看 Day 1 笔记，写出模型的 `D/H/KvH/I/V/L` 实际数值或标出尚未找到的项。
答：

本题模型为 `deepseek-r1-1.5b-f16.gguf`（Qwen2 架构）。从 GGUF metadata 与 tensor shape 可得到：

| 符号 | 含义 | 实际值 | 对应字段或依据 |
| --- | --- | ---: | --- |
| `D` | hidden size / embedding length | `1536` | `qwen2.embedding_length`；`token_embd.weight` 的 hidden 维 |
| `H` | Query attention head 数 | `12` | `qwen2.attention.head_count` |
| `KvH` | Key/Value head 数 | `2` | `qwen2.attention.head_count_kv` |
| `I` | FFN intermediate size | `8960` | `qwen2.feed_forward_length`；`ffn_gate/up.weight` 的中间维 |
| `V` | vocabulary size | `151936` | `token_embd.weight` 的词表维 |
| `L` | Transformer block/layer 数 | `28` | `qwen2.block_count` |

补充：`Dh = D / H = 1536 / 12 = 128`；因此 K/V 总维度为 `KvH * Dh = 2 * 128 = 256`。

## 习题2
读通用 hparams**：阅读 [`src/llama-model.cpp`](../../src/llama-model.cpp) 的 `llama_model_base::load_hparams()`，定位通用的 context length、embedding length、block count、metadata copy 和 `rope_type` 设置。阅读 [`src/models/llama.cpp`](../../src/models/llama.cpp) 的 `llama_model_llama::load_arch_hparams()`，区分“所有模型共有的 hparams”与“Llama 架构特有的 hparams”。

答：

`llama_model_base::load_hparams()` 是公共加载入口，它先处理各架构共享的字段，再调用虚函数 `load_arch_hparams(ml)` 让具体架构补充自己的字段。
该函数先复制 metadata 并读取 `general.name`；若是 `vocab_only` 模式或 CLIP 架构，会在此处提前返回，不再加载后续数值 hparams。

### 通用部分

| 代码位置 | GGUF key | 写入目标 | 含义 |
| --- | --- | --- | --- |
| `src/llama-model.cpp:1089` | `LLM_KV_CONTEXT_LENGTH` | `hparams.n_ctx_train` | 模型训练时的 context length，不是运行时 `n_ctx` |
| `src/llama-model.cpp:1090` | `LLM_KV_EMBEDDING_LENGTH` | `hparams.n_embd` | hidden/embedding 维度 `D` |
| `src/llama-model.cpp:1094` | `LLM_KV_BLOCK_COUNT` | `hparams.n_layer_all` | 总 block/layer 数，随后检查它在 `1..LLAMA_MAX_LAYERS` 内 |

同一通用函数还读取或初始化 output embedding length、causal attention、pooling、expert 数、每层 FFN 维度、Query/KV head 数、RoPE 缩放参数、head 维度和 rotary 维度等共享字段。其中 `n_head_kv_arr` 先默认为 `n_head_arr`，GGUF 提供 `ATTENTION_HEAD_COUNT_KV` 时才覆盖，因此 MHA 是默认情况，GQA/MQA 需要额外 metadata。

metadata copy 位于 `src/llama-model.cpp:1069-1078`：它遍历 GGUF 的 key-value，跳过 `GGUF_TYPE_ARRAY`，将其他值转为字符串后存入 `model->gguf_kv`。因此这是一份供查询/展示的“非数组 metadata 字符串副本”，不是将整个 GGUF metadata 原样复制。`general.name` 随后单独读入 `model->name`。

`rope_type` 也不是在这里直接从 GGUF key 读取。通用函数先在 `src/llama-model.cpp:1235` 调用架构专用钩子，然后在第 1247 行调用 `llama_model_rope_type(this)`，根据 `model->arch` 派生 `hparams.rope_type`。`LLM_ARCH_LLAMA` 在该 `switch` 中返回 `LLAMA_ROPE_TYPE_NORM`。这个“RoPE 维度的配对/排列方式”与从 metadata 读取的 `hparams.rope_scaling_type_train` 是两个不同概念。

### Llama 架构专用部分

`llama_model_llama::load_arch_hparams()` 很短，它本身只做两件事：

1. 读取 `VOCAB_SIZE`（缺失时用 tokenizer list 的长度）到局部变量 `n_vocab`，并读取 Llama 所需的 `ATTENTION_LAYERNORM_RMS_EPS` 到 `hparams.f_norm_rms_eps`。后者是这个函数真正新增的 Llama 架构 hparam。
2. 利用已由通用阶段读取的 `n_expert`、`n_layer()`、`n_head()`/`n_head_kv()`，再结合局部 `n_vocab`，推断 `model->type`（如 `1B`、`7B`、`8B`、`70B`）。`type` 是用于模型分类/展示的派生结果，不是新的 GGUF hparam。

所以边界可以概括为：`n_ctx_train`、`n_embd`、`n_layer_all`、head/FFN/RoPE 的通用配置由 `llama_model_base` 管理；Llama 钩子只补充 Llama 所需的 RMSNorm epsilon 并判定模型规模类型。

## 习题3
做一次配置推导**：以真实数值补全以下数据流，不要求创建任何 tensor：

   ```text
   hidden [N, D]
     -> Q [N, H, Dh]
     -> K/V [N, KvH, Dh]
     -> score [H, N, S]
     -> attention output [N, D]
     -> SwiGLU intermediate [N, I]
     -> block output [N, D]
     -> logits [N, V]
   ```

   `N` 是本次 decode 输入 token 数，`S` 是包含历史 KV 的可见长度。写明 `N` 与训练 context length、运行时 `n_ctx` 都不是同一概念。

答：

本题模型的已知参数为：

```text
D   = 1536
H   = 12
KvH = 2
Dh  = D / H = 1536 / 12 = 128
I   = 8960
V   = 151936
L   = 28
```

代入后，单个 Transformer block 的逻辑数据流为：

```text
hidden                 [N, 1536]
  -> Q                 [N, 12, 128]
  -> K/V               [N,  2, 128]  (K 和 V 各一份)
  -> attention score   [12, N, S]
  -> attention heads   [N, 12, 128]
  -> attention output  [N, 1536]
  -> SwiGLU gate/up     [N, 8960]     (gate 和 up 各一份)
  -> SwiGLU product     [N, 8960]
  -> FFN down           [N, 1536]
  -> block output       [N, 1536]
```

这个 block 结构重复 `L=28` 次。最后一层的 block output 经 final norm 后 shape 仍为 `[N, 1536]`，再由 output projection 映射到词表维：

```text
final hidden [N, 1536]
  -> logits  [N, 151936]
```

### Attention 维度为什么这样

- Q 的总维度是 `H * Dh = 12 * 128 = 1536`，所以可从 `[N, 1536]` reshape 为 `[N, 12, 128]`。
- 当前 `N` 个 token 各自生成 K 和 V，每份的总维度只有 `KvH * Dh = 2 * 128 = 256`，因此 shape 为 `[N, 2, 128]`。
- 此模型使用 GQA，`H / KvH = 12 / 2 = 6`，即每 `6` 个 Query head 共享 `1` 个 K/V head。计算时 K/V 在 Query head 维上按组复用，所以 score 仍有 `H=12` 个 head，shape 为 `[12, N, S]`。
- score 对可见的 `S` 个 Value 位置做加权求和，得到 `[N, 12, 128]`；合并 12 个 head 后回到 `[N, 1536]`。
- SwiGLU 的 gate 分支和 up 分支都扩展到 `I=8960`，逐元素门控后仍是 `[N, 8960]`，再由 down projection 压回 `[N, 1536]`，才能与 residual 相加。

### `N`、`S` 和两种 context length

| 量 | 本题中的含义 | 是否固定 |
| --- | --- | --- |
| `N` | 本次 `llama_decode` 送入的 token 数；prompt prefill 时通常大于 1，逐 token 生成时通常为 1 | 每次 decode 可变 |
| `S` | 某个 Query 能看到的 KV 位置数，包括已缓存的历史和当前 batch 中通过 causal mask 的位置 | 随已接受 token 增长，也受 mask/滑动窗口影响 |
| `n_ctx_train=32768` | GGUF metadata 记录的训练 context length，表示模型训练时的上下文尺度 | 模型文件属性 |
| 运行时 `n_ctx` | 创建 llama context 时配置的上下文容量，约束推理时可保留/处理的上下文 | 由运行参数决定 |

因此，`N` 是“这一次计算多少个新 token”，`S` 是“当前 Query 能关注多少个位置”，`n_ctx_train` 是训练尺度，运行时 `n_ctx` 是推理容量。`N` 不等于后两者，`S` 也不是固定的 `n_ctx`；图中 `[12, N, S]` 是忽略 causal mask 造成的逐 Query 可见长度差异后的逻辑 shape。

## 习题4
估算 KV cache**：只按 K/V 的元素数估算单层、单 sequence 的最小 cache 数据量：

   ```text
   elements per layer = 2 * S * KvH * Dh
   bytes per model   = 2 * S * KvH * Dh * L * bytes_per_element
   ```

   分别用 `S=128` 和计划使用的 `n_ctx` 计算。记录 cache type 的假设，例如 F16 是 2 bytes；不要把该估算误写成实际 `llama_memory_i` 分配大小。

答：

本题沿用前面得到的模型参数：

```text
KvH = 2
Dh  = 128
L   = 28
```

假设 K cache 和 V cache 都使用 F16，即每个元素 `2 bytes`。此处的系数 `2` 表示 K 和 V 各一份：

```text
单层元素数 = 2 * S * KvH * Dh
单层字节数 = 2 * S * KvH * Dh * 2
全模型元素数 = 2 * S * KvH * Dh * L
全模型字节数 = 2 * S * KvH * Dh * L * 2
```

### `S=128`

```text
单层元素数
= 2 * 128 * 2 * 128
= 65,536 elements

单层字节数
= 65,536 * 2
= 131,072 bytes
= 128 KiB

全模型元素数
= 65,536 * 28
= 1,835,008 elements

全模型字节数
= 1,835,008 * 2
= 3,670,016 bytes
= 3,584 KiB
= 3.5 MiB
```

### `S=n_ctx=4096`

这里的“计划使用的 `n_ctx`”取前面学习记录中的 `4096`。当 cache 填满时取 `S=4096`：

```text
单层元素数
= 2 * 4096 * 2 * 128
= 2,097,152 elements

单层字节数
= 2,097,152 * 2
= 4,194,304 bytes
= 4 MiB

全模型元素数
= 2,097,152 * 28
= 58,720,256 elements

全模型字节数
= 58,720,256 * 2
= 117,440,512 bytes
= 114,688 KiB
= 112 MiB
```

| 可见长度 `S` | 单层 K+V 元素数 | 单层 F16 字节数 | 28 层 K+V 元素数 | 28 层 F16 字节数 |
| ---: | ---: | ---: | ---: | ---: |
| `128` | `65,536` | `128 KiB` | `1,835,008` | `3.5 MiB` |
| `4096` | `2,097,152` | `4 MiB` | `58,720,256` | `112 MiB` |

这是“单 sequence、所有 28 层、只计 K/V 有效元素”的理论最小值，且默认每层都使用相同的 `KvH=2`、`Dh=128` 和 F16 cache。它不是实际 `llama_memory_i` 的分配量：真实实现还可能受 cache 容量取整/填充、对齐、多 sequence、不同 K/V 类型、后端 buffer 及其他管理开销影响。KV cache 是推理时状态，也不是 GGUF 文件中保存的模型权重。

## 习题5
口述：用“模型文件提供的数字”解释 GQA 如何减少 K/V 权重和 cache，而不会减少 Q head 数。

答：

可以这样口述：

> 这个模型的 GGUF 提供 `D=1536`、`H=12`、`KvH=2`，因此每个 head 的维度是 `Dh=D/H=128`。Q 仍有 12 个 head，总输出维度是 `12*128=1536`；K 和 V 则各只有 2 个 head，总输出维度都是 `2*128=256`。所以 Q 权重仍是 `[1536,1536]`，K/V 权重各缩小为 `[256,1536]`。`H/KvH=12/2=6`，即每 6 个 Query head 共享 1 个 K head 和 1 个 V head。因此 K/V 权重和 KV cache 都只需普通 12-head MHA 的 `1/6`，但 Q 仍保留 12 个 head，attention score 也仍是 `[12,N,S]`。GQA 减少的是独立 K/V head 的数量，不是 Query head 的数量。

### 权重对比

下表只计权重矩阵，不计 bias。逻辑 shape 使用 `[out,in]`：

| 投影 | 实际 GQA shape | 实际元素数 | F16 字节数 | 假设 `KvH=H=12` 的 MHA 元素数 |
| --- | ---: | ---: | ---: | ---: |
| Q | `[1536,1536]` | `2,359,296` | `4.5 MiB` | `2,359,296` |
| K | `[256,1536]` | `393,216` | `0.75 MiB` | `2,359,296` |
| V | `[256,1536]` | `393,216` | `0.75 MiB` | `2,359,296` |
| K+V | - | `786,432` | `1.5 MiB` | `4,718,592` (`9 MiB` F16) |

GGUF 中 `blk.0.attn_q.weight` 的 `ne=(1536,1536)`，`blk.0.attn_k.weight` 和 `blk.0.attn_v.weight` 的 `ne=(1536,256)`，正好验证了上述数字（GGML `ne[]` 的显示顺序与表中的逻辑 `[out,in]` 相反）。单层 K+V 权重由假设 MHA 的 `9 MiB` 减少到 `1.5 MiB`，为原来的 `1/6`；28 层合计则从 `252 MiB` 减少到 `42 MiB`。Q 权重完全不变。

### KV cache 对比

对每层每个 token：

```text
GQA K+V = 2 * KvH * Dh = 2 * 2  * 128 =   512 elements
MHA K+V = 2 * H   * Dh = 2 * 12 * 128 = 3,072 elements
```

所以对任意可见长度 `S`，GQA 需要 `512*S` 个 K/V 元素，MHA 则需要 `3072*S` 个，仍然相差 6 倍。按 F16、28 层、单 sequence 估算：

| `S` | 实际 GQA cache | 假设 MHA cache | GQA / MHA |
| ---: | ---: | ---: | ---: |
| `128` | `3.5 MiB` | `21 MiB` | `1/6` |
| `4096` | `112 MiB` | `672 MiB` | `1/6` |

推理时每个 K/V head 被 6 个 Query head 按组复用，因此不需要在 cache 中为 12 个 Query head 各存一份 K/V。Q 只为当前 decode 计算，不作为历史 KV cache 保存；它仍保留 12 个 head，所以可以产生 12 组不同的 Query 表示。

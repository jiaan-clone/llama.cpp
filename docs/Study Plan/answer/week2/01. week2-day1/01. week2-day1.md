## 习题1
 **0-10 分钟，闭卷回忆**：从第 1 周的单层图写出 `D`、`H`、`KvH`、`Dh`、`I`、`V` 的含义，以及 `Dh = D / H` 在普通 Llama attention 中成立的前提。
 答：
 - `D`：hidden size / embedding length，单个 token 的隐藏向量维度。
- `H`：Query attention head 数。
- `KvH`：Key/Value head 数。GQA 中通常 `KvH <= H`，多个 Q head 共享一组 K/V head。
- `Dh`：每个 attention head 的维度。
- `I`：FFN 的中间维度，通常大于 `D`。
- `V`：词表大小，也是 logits 的最后一维。

`Dh = D / H` 成立的前提是：普通 Llama attention 将长度为 `D` 的隐藏表示均匀切分为 `H` 个 Query head，且 `D` 能被 `H` 整除。因此：

```text
Q: [N, D] -> [N, H, Dh]
D = H * Dh
```

GQA 只减少 K/V 的 head 数，不改变 Q 的 `H * Dh = D` 关系：

```text
K/V: [N, D] -> [N, KvH, Dh]
```

若某个架构为 Q、K、V 使用不同 head dimension，或其 `n_embd` 不等于 `n_head * n_embd_head`，则不能直接套用 `Dh = D / H`，应以模型 metadata 和源码中的实际 hparams 为准。

## 习题2
区分 GGUF 三类数据**：阅读 [`ggml/src/gguf.cpp`](../../../../../ggml/src/gguf.cpp)，只定位 `gguf_context`、`gguf_kv`、`gguf_tensor_info` 的定义。画出 `header -> kv metadata -> tensor info -> aligned tensor data` 四段图，并写清 tensor info 包含 name、type、dimensions、data offset，而不等于 tensor data 本身。

答：
GGUF 可分为三类核心数据：KV metadata、tensor info、tensor data。文件开头的 header 用来说明如何解析它们。

```text
GGUF file
|
+-- Header
|   - magic: "GGUF"
|   - version
|   - n_tensors
|   - n_kv
|
+-- KV metadata
|   - key + type + value
|   - 例如 general.architecture、llama.embedding_length、
|     llama.attention.head_count、tokenizer.ggml.tokens
|
+-- Tensor info
|   - 每个权重的一条目录记录
|   - 例如 blk.0.attn_q.weight
|   - name、type、n_dims、dimensions、offset
|
+-- Aligned tensor data
    - 真正的权重字节
    - 按 tensor info 的 offset 定位
    - 每个 tensor 起点满足 alignment 要求
```

在 [`gguf.cpp`](/home/king/llama.cpp/ggml/src/gguf.cpp:181) 中：

- `gguf_context`：整个 GGUF 的内存表示，保存版本、`kv` 列表、tensor info 列表、alignment、tensor data 区域信息等。
- `gguf_kv`：一条 metadata，包含 `key`、是否为数组、GGUF 类型，以及实际 value 数据。例如模型架构名、层数、词表信息。
- `gguf_tensor_info`：一条 tensor 的描述信息，内部用 `ggml_tensor t` 保存 tensor 的 name、type、维度 `ne[]` 等元信息，另有 `offset`。

关键区别是：

```text
tensor info = “这块权重在哪里、形状和类型是什么”
tensor data = “这块权重的实际数值字节”
```

例如：

```text
name:       blk.0.attn_q.weight
type:       F16
dimensions: [D, H * Dh]       # 具体顺序以 GGML ne[] 为准
offset:     123456789

tensor data:
  从 tensor-data 起始地址 + 123456789 开始的连续字节，
  才是真实的 Q projection 权重值。
```

因此，loader 可以先用 `no_alloc = true` 读取 header、metadata 和 tensor info，完成架构识别、shape 校验与模型对象创建；此时并没有把全部权重数值加载到 tensor buffer。真正读取、映射或上传 tensor data 是后续 `load_tensors()` 和 `load_all_data()` 阶段的工作。

### 3. 为什么逻辑 shape 和 `ne[]` 顺序相反？

计划中的逻辑 shape 按矩阵乘法语义表示，例如：

```text
Q projection: [output_dim, input_dim]
             = [1536, 1536]

FFN gate:     [output_dim, input_dim]
             = [8960, 1536]
```

而 GGML 中权重通常按：

```text
ne[0] = input_dim
ne[1] = output_dim
```

保存，因此：

```text
ffn_gate.weight:
逻辑 shape = [8960, 1536]
GGML ne[]   = (1536, 8960)
```

这不是维度错误，而是逻辑矩阵表示和 GGML 存储/运算约定不同。

### 4. 与日志的对应关系

日志可以直接验证：

```text

ne = (1536, 151936)

blk.0.attn_q.weight:
ne = (1536, 1536)

blk.0.attn_k.weight:
ne = (1536, 256)

blk.0.attn_v.weight:
ne = (1536, 256)

blk.0.ffn_gate.weight:
ne = (1536, 8960)

blk.0.ffn_down.weight:
ne = (8960, 1536)
```

例如：

```text
K/V 总维度 = 256
Dh          = 128
KvH         = 256 / 128 = 2
```

因此，当前模型可以填写为：

```text
D=1536, H=12, KvH=2, Dh=128, I=8960, V=151936
```

需要标注的假设是：`Dh = D / H` 以及上述 Q/K/V 命名和 shape 适用于这个 Qwen2 模型，但不能无条件推广到所有模型架构。若模型使用独立的 `head_dim`、不同的 Q/K/V head dimension 或特殊投影布局，应以对应模型源码和 metadata 为准。

### 4. 对照表

| 权重 | 逻辑 shape | GGML `ne[]` | 元素数量 |
| --- | --- | --- | ---: |
| Q projection | `[1536, 1536]` | `(1536, 1536)` | `2,359,296` |
| K projection | `[256, 1536]` | `(1536, 256)` | `393,216` |
| FFN gate | `[8960, 1536]` | `(1536, 8960)` | `13,762,560` |

逻辑 shape 通常按 `[输出维度, 输入维度]` 表示，而 GGML 权重的 `ne[]` 通常按 `(输入维度, 输出维度)` 保存，所以非方阵权重看起来是反过来的。

### 5. 为什么 `KvH < H` 时 K/V 投影更小？

这是 GQA 的结果：

```text
Q head 数 = H   = 12
K/V head 数 = KvH = 2
每个 head 维度 = Dh = 128
```

因此：

```text
Q 输出维度  = 12 * 128 = 1536
K/V 输出维度 = 2 * 128  = 256
```

每个 K/V head 被多个 Q head 共享：

```text
每个 K/V head 服务 H / KvH = 12 / 2 = 6 个 Q head
```

所以 K/V projection 的输出维度和参数量约为 Q projection 的：

```text
KvH / H = 2 / 12 = 1/6
```

这会同时减少：

- K/V 投影权重大小；
- KV cache 的 head 维度；
- decode 阶段保存历史 K/V 所需的内存。

FFN gate 的元素数量更大，是因为它把 hidden size 从 `D=1536` 扩展到中间维度 `I=8960`。

### 习题3 作用
这个问题的目的，是为后续源码阅读建立“真实模型配置基线”，避免只用抽象符号或猜测模型结构。

它具体帮助你：

- 确认模型实际架构，例如 `qwen2`，后续应读对应的模型实现，而不能按 Llama 的字段和细节照搬。
- 把 `n_embd`、`n_head`、`n_head_kv`、`n_ff`、`n_layer`、`n_vocab` 转成真实数字，用于 Day 2 推导 Q/K/V、FFN、KV cache 的 shape 和内存量。
- 从 tensor 名称、类型、大小、offset 建立“GGUF 文件内容 -> `create_tensor()` -> model buffer”的追踪起点。
- 判断是否分片：存在 `split.count` 时，loader 需要继续发现、校验并加载其他 GGUF 文件。
- 确认 tokenizer、特殊 token 与 chat template 都是模型文件的一部分，而非推理程序随意附加的配置。
- 通过 `general.quantization_version`、`general.file_type` 和 tensor type 分辨权重格式，为第 7 周量化学习做准备。

保存原始输出的作用是保留可复查证据。后续你写的 shape 表、加载调用图和实验结论，都能回到同一份模型档案核对。
